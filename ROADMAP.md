**IMPORTANT for any session running the test suite:** `tests/conftest.py` now isolates the real Season save file (`data/saves/current_season.json`) for the whole pytest run -- read that file's own docstring before touching `season_state.py`'s save/load path or `save_service.DEFAULT_SAVE_PATH`. Before this fix (discovered during M12), running `pytest tests/` with a real franchise save on disk would silently overwrite it, with no error and no warning -- the live app server never noticed because it only reads the save once per process.

**IMPORTANT, second incident (discovered during M14, real damage occurred): there is a THIRD persistence surface, `app.core.db.DB_PATH` (`data/franchise_football.db`, the real Player roster/ratings database), separate from both `save_service.DEFAULT_SAVE_PATH` and `history_store.DEFAULT_PATH`.** `season_state.start_new_season()` calls `apply_progression_to_roster()`, which ages/re-rates every rostered player and commits it straight to whatever `app.core.db.DB_PATH` currently points to. A standalone verification script (run OUTSIDE pytest, to produce real HOF inductees for M14's testing) redirected the season-save and history paths correctly but never knew this third path existed -- it ran `start_new_season()` several times against the REAL, live `data/franchise_football.db`, with no in-memory cache anywhere to fall back on (unlike the M12 incident, where another process's cached season state made recovery possible). **Actual damage: 93% of all 2,365 players ended up at Overall Rating 0, 97% at age 45+.** No git history existed for this file (gitignored) and no backup was found anywhere. Recovered the ONLY way available -- re-ran `scripts/import_players.py` to rebuild the roster from the real CSV baseline (`data/raw/rosters/`) -- which restores a fully sane, playable database but **permanently loses every bit of in-game progression/regression/aging the franchise had accumulated across its real simulated seasons** (a previous session, M8, had explicitly avoided this exact tradeoff for this exact reason; this time it was already unavoidable, since the corruption had already destroyed that history before the tradeoff was even a choice). The corrupted DB was backed up before the fix in case anything is salvageable from it, but nothing in this repo currently reads it.

**Good news confirmed while investigating:** the pytest suite itself was NEVER at risk from this -- `test_season_rollover.py` and `test_history_store.py` (the only 2 files calling `start_new_season()`/`apply_progression_to_roster()`) both already correctly copy the real DB to a throwaway file and redirect `db_module.DB_PATH` per-test, restoring it afterward regardless of outcome. This was purely a standalone-script hygiene gap, not a test-infrastructure one -- **any future one-off verification script that calls `season_state.start_new_season()` (directly or via simulating a full season through playoffs+archival) MUST manually redirect all THREE of `save_service.DEFAULT_SAVE_PATH`, `history_store.DEFAULT_PATH`, AND `app.core.db.DB_PATH` (via `db_module.DB_PATH = <throwaway>; db_module._engine = None` to force the engine to rebuild against it) BEFORE importing/using `season_state` at all** -- see `test_season_rollover.py`'s own `_isolated_db_and_saves` fixture for the exact, correct pattern to copy.

**Third incident (2026-09-12, during R1's injury-system build, real damage occurred): a standalone smoke-test script called `season_state.reset_season()`/`simulate_current_week()` directly, with NO path redirection at all** -- not even the save/history paths this section's first incident already covers, let alone `db_module.DB_PATH`. Ran several times against the REAL `data/saves/current_season.json` and `data/saves/power_rank_history.json`. **Actual damage: the user's real in-progress KC franchise (user_team_abbr="KC", week 6, 5-0 record, confirmed rendered live in the Browser pane earlier this same session during A2 verification) was overwritten** -- `current_season.json` now reads `user_team_abbr: None, current_week: 1, season_number: 25` (a fresh reset, plus 18 more weeks of unrelated test simulation on top). No git history for this gitignored file. **Unlike the M14 incident, there IS a real chance of recovery**: a separate chat's dev server (confirmed still running on port 8010 at the time of the mistake, per this session's own earlier `preview_start` port-conflict message) may still hold the correct pre-overwrite `Season` object in its process memory (`season_state.py`'s `_season` module global loads from disk only once per process) -- if that process is still alive and eventually calls anything that re-saves (`simulate_current_week()`, `set_user_team()`, etc.), it will silently overwrite this session's damage with the correct state. Not confirmed either way as of this writing. **This was a real, avoidable repeat of a documented mistake** -- the session had already read this exact section earlier in the same conversation before making it. **Engine integration — this is the part that makes it more than a roster page (R3b).** New `app/engine/coaching.py` reduces a staff to a `StaffEffect` and plugs into the exact call sites `gameplan.py` already threads through (`drive_sim.py`, `defensive_ai.py`, `game_sim.py`, `season_state.py`), taking `StaffEffect | None` with a zero bias for `None`. **The important difference from Gameplan: a gameplan exists only for the user's team, but a staff exists for all 32** — so this is the first system giving every AI team its own play-calling identity instead of every team calling from the identical league-average baseline. Centering the penalty-rate and development multipliers on a hardcoded 50 therefore gave **every** team a ~0.8x penalty multiplier and a ~1.10x development multiplier — a silent league-wide shift to rates `tuning.py` and `test_stat_realism.py` have calibrated, rather than the per-team differentiation the system is for. ### 4c-addendum-2. A1 — Roster Strength aggregator built (2026-09-11)

**Status: A1 done. A2 (position-rank sheet), A3 (tuning pass), A4 (prestige) still open** — see `docs/handoff_prestige_and_coach_impact.md`. There was no roster-to-team-strength aggregator anywhere in this codebase before this; `app/engine/scouting.py` is entirely in-season play-derived and `app/engine/rating.py`'s `TeamRatings` is a dead placeholder ([[project_sim_strength_is_player_level]]) — neither can produce a week-0 number.

**The design calls (Brian, this session):**
- **Group aggregation is snap-share weighted** — `app/engine/roster_strength.py` reuses `app/engine/rotation.py`'s real per-position decay curves (they already encode genuine playing-time share, which is exactly what a strength weight should track) wherever rotation.py models that position, and adds a new `IRON_MAN_DECAY` (steeper than rotation.py's own steepest, `DB_DECAY`) for the positions the live sim never rotates at all: QB, every OL slot, both safety spots, K, P.
- **Starter/depth split lands at "heavy starters" (~80/20) as a roster-wide average**, not a uniform per-group knob — some groups run more bench-heavy (WR, via `WR_DECAY=0.80`) and some almost pure iron-man (S, via the new `IRON_MAN_DECAY=0.10`), the same real variance the live sim's own rotation already has.
- **Coach contribution is additive**: `COACH_WEIGHT = 0.15` blends `Coach.overall` as its own term onto `roster_score` rather than scaling it, so a strong coach can lift a weak roster's `team_rating`, not just move it toward zero. 0.15 was chosen so the coach's share of the final number (15%) lands close to QB's own effective share (~17%) — "heavy," comparable to the single most important position weight, not dominant over the rest of the roster.
- **Positional weights (`POSITION_WEIGHTS`) are an explicitly first-pass placeholder**, not a tuned result. Only one claim is actually settled and asserted in code: QB's weight (3.00) clearly exceeds K+P combined (0.50). Every other weight is this module's own ordering, and **A3's tuning pass (simulate seasons, correlate this rating against final record/Elo, adjust to match observed sensitivity) is required before they should be trusted** — not done in this chunk.
- **Position groups reuse the Roster page's existing 14-group taxonomy** (QB/RB/WR/TE/C/G/T/DE/DT/LB/CB/S/K/P) rather than inventing a second one — pulled out of `app/main.py` into a new shared `app/engine/position_groups.py` (`main.py` now imports from there; no behavior change, verified by the full suite).
- **Persistence/storage deliberately NOT done here.** The handoff's own suggestion — a week-0 snapshot in `power_rank_history.py` — has no consumer yet (A2's sheet doesn't exist), so wiring storage now would be a store nothing reads. That lands together with A2.

**Verification:** 11 new tests in `tests/test_roster_strength.py` — pure-function tests for snap-share weighting, multi-position group averaging, and weight renormalization (hand-built `Player` rows, no DB); read-only real-DB tests for the coach blend, the no-coach degrade case, and all 32 real teams computing all 14 groups within 0-99 bounds. ### 4c-addendum-4. A3 — the tuning pass, run and applied (2026-09-12)

**Status: A3 done** (first real pass — see caveats below, further refinement is a legitimate future task, not a blocker). `scripts/tune_roster_strength_weights.py` implements A3's own instructed method exactly: correlate the fixed preseason rating against real simulated outcomes, and check that varying one position group in isolation moves outcomes by about the amount its weight claims.

**Part 1 — correlation** (14 seeds, real unmodified DB, pooled n=448 team-season pairs): `team_rating` vs final `win_pct` r=+0.429 (rho=+0.449); `team_rating` vs final `power_rating` r=+0.485 (rho=+0.506); `roster_score` alone (no coach blend) vs `win_pct` r=+0.535 — a real, moderate, honest predictive signal (not fabricated near-1.0, and not zero either). Worth noting for anyone revisiting `COACH_WEIGHT`: the coach blend correlated *slightly worse* with actual win_pct than roster talent alone did in this run — not by enough to justify changing `COACH_WEIGHT` off one run, but a data point if A3 gets a deeper follow-up.

**Part 2 — sensitivity** (3 seeds x 6 groups, swapping a mid-pack baseline team's REAL roster at one group for the league's actual best team's real players at that group, same-seed paired comparison, throwaway DB copy per trial): **T (offensive tackle) measured essentially tied with QB** at the top of observed sensitivity — both far above every other tested group. This tracks a real mechanism, not noise: `app/models/player.py`'s own module docstring documents a direct "LT & LG vs. opponent RDE & RDT" zone-blocking matchup formula the sim actually runs. WR and DE measured statistically indistinguishable from each other. LB measured well below its old weight. K measured at/below zero, consistent with (not evidence to lower further than) its already-low weight.

**Weights changed** (`app/engine/roster_strength.py`'s `POSITION_WEIGHTS`): T 1.00→3.00 (the big correction — directly measured), DE 1.25→1.50 (measured), LB 1.25→0.75 (measured), G 0.75→1.25 and C 0.50→0.75 (inferred from T's result, same blocking-matchup family per `player.py`'s docstring — flagged separately from the directly-measured groups). QB/WR/K essentially confirmed, unchanged. **RB/TE/DT/CB/S/P were not tested and are unchanged placeholders** — this pass covered 6 of 14 groups directly, 2 more by reasoned inference, 6 remain untested.

**Two real bugs caught building this script, both fixed before trusting any result from it:**
1. The sensitivity swap originally moved donor's players OUT with nothing given back, leaving the donor team with **zero** players at that position group — which doesn't just skew donor's own record, it hard-crashes `depth_chart.py`'s `_top()` the instant donor's own game simulates (`IndexError: list index out of range`, every team plays every week). Fixed by making it a real two-way swap (baseline gets donor's players, donor gets baseline's original players at that position) rather than a one-way theft.
2. Windows kept the throwaway scratch DB file locked after `db_module._engine = None` — dropping a Python reference doesn't synchronously close SQLAlchemy's pooled connections, so the next `shutil.copy`/`unlink` over the same path hit a real `PermissionError: [WinError 32]`. Fixed with an explicit `.dispose()` before nulling the engine reference.

**Caveats (printed by the script itself, worth repeating here):** 2-3 seeds per group is enough to catch a badly-wrong ordering, not to pin exact weight values to two decimal places — a stochastic sim's per-season win_pct variance is large relative to one team's group-strength swap. `power_rating` (Elo) is the steadier signal of the two measured; `win_pct` over one 18-game season is noisier by nature. The swap size also reflects how far apart the league's actual best and the baseline team happen to be at that group today, not a fixed-size intervention — read the results as "does the ordering make sense," not as a precise per-point conversion rate.

**Verification:** `tests/test_roster_strength.py` unaffected (no test hardcodes a specific weight value) — 11 passed. Full suite: 323 passed, 1 skipped, re-run after applying the new weights.

## 4j. Sim-speed investigation — one real fix shipped, two larger ones found and deliberately NOT shipped (2026-09-13)

Brian asked "the sim takes too long, are there ways to make it faster?" Measured before touching anything: `cProfile` against an isolated throwaway DB copy over a full 18-week regular season + 4 playoff rounds + one `start_new_season()` rollover — 153.6 real seconds, ~6.9s/simulated week on average, 107M function calls.

**Shipped (safe, isolated, tested): `draft_pick_store.py`'s `owner_of()` N+1.** `app/engine/draft.py`'s `simulate_draft()` called `owner_of()` once per (round, team) — 224 times for a full 7-round/32-team draft — and each call re-read and re-parsed the ENTIRE pick-inventory JSON file from disk (measured: 220ms for 224 calls against a 672-entry inventory). Fixed with a new `owners_for_season()` bulk read, called once up front, same "fetch once, update in memory" precedent this exact function already follows for `_all_teams_group_counts()` (§4f). `tests/test_draft.py`'s existing traded-pick test mocked the now-unused `owner_of()`; updated it to mock `owners_for_season()` instead — same intent, correct target.

**Found, NOT shipped: `coach_store`'s league-wide cache thrashing.** `app/services/coach_ai.py`'s per-week AI firing pass (`run_inseason_autonomy()`) calls `coach_replacement.execute_fire()`/`execute_hire()` per event, and EACH of those unconditionally clears `coach_store`'s entire league-wide `lru_cache` (`all_coaches()`/`staff_for()`, keyed for the WHOLE league, not per-team) — profiled at ~21-22s cumulative across 1601/633 calls, consistent with mostly cache MISSES (a real hit would cost microseconds, not the observed ~14ms/call average). First attempt: added a `clear_cache: bool` param threaded through `execute_fire()`/`execute_hire()`/`apply_new_hc_effect()`/`renew_contract()`/`_evaluate_team()` so a per-team-loop caller could defer to one clear at the end instead of one per event. **This introduced a real, caught-before-commit correctness bug**: deferring the clear across ALL 32 teams in one pass let `apply_new_hc_effect()`'s own internal `staff_for()` read stale data from an EARLIER team's fire/hire in the same pass, and in one seeded full-season run this produced a champion team with a permanently vacant HC seat (`tests/test_coaching.py::test_championship_credit_lands_on_every_role_and_is_idempotent` failed: `roles_present == {AC}`, no HC at all). Confirmed via `git stash` that the pre-fix baseline passes this exact test clean. **Reverted entirely** (`app/engine/coach_contracts.py`, `app/engine/coach_replacement.py`, `app/services/coach_ai.py` restored to HEAD) rather than ship a save-corrupting risk under time pressure — this needs a design that's safe ACROSS teams (e.g. per-team cache invalidation instead of one global `lru_cache(maxsize=1)`, or restructuring `_evaluate_team()` to fully resolve one team's own fire/hire/purge chain against a local, always-fresh view before moving to the next team), not a blanket "defer and batch," and deserves its own session with headroom to design and verify it properly.

**Found, NOT shipped: `save_service.py`'s O(n²) season re-serialization.** `season_to_dict()` → `_week_games_to_dict()` re-serializes EVERY week's full play-by-play (`dataclasses.asdict()` on every `DriveEvent`/`PlayEvent` of every game of every ALREADY-PLAYED week), every single time `save_season()` is called — which is every week. A played week's `GameResult` never changes once recorded, so this is pure repeated work that grows every week, called every week: `dataclasses.asdict()`/`_asdict_inner()` profiled at 756,155 calls / 11.8M recursive inner calls / ~22.5s combined; `save_season`→`season_to_dict`→`_result_to_dict`→`_week_games_to_dict` each profiled at 23-29s cumulative. The real fix (cache each COMPLETED week's already-serialized dict form, keyed off the season object, recompute only the in-progress week + top-level mutable fields each save) touches the core save-file hot path used by every save/load in the app — flagged for Brian to decide on, not attempted blind under a "wrap this up fast" constraint.

Full suite after the shipped fix: 93 of the directly-affected tests (`test_draft.py`, `test_draft_pick_store.py`, `test_trades.py`, `test_coaching.py`) pass clean.

## 5. How to actually run this efficiently (the token-saving playbook)

This session (the one that produced this file) is enormous — every remaining turn in it re-sends its entire history. That's the single biggest thing to avoid going forward.

1. **One chunk = one fresh Claude Code chat.** Don't continue this session for the next chunk. A new chat starts with an empty context window; it only grows with what that chunk actually needs.

2. **Open each new session with a tight, direct prompt** — not "explore the codebase and figure out what to do." Use this template:

   > Read `HANDOFF.md` and `ROADMAP.md`. Implement chunk **[M1/M2/M3/...]** as scoped in ROADMAP.md §2 (or §4). Relevant files: [copy the "Key files" column]. Follow the existing patterns in those files — don't redesign anything not in scope. Run the test suite before committing.

   Naming the exact chunk ID and files means the fresh session doesn't spend tokens re-discovering what this file already tells it.

3. **Match the model to the chunk** (see the tables above):
   - **Sonnet 5** (this session's model) — the right default for most implementation work. Good capability-to-cost balance.
   - **Haiku 4.5** — for mechanical, low-ambiguity chunks where the hard thinking is already done (M3, M4: a real Figma source file just needs translating into the existing template pattern). Meaningfully cheaper; don't pay Sonnet/Opus prices for a translation job.
   - **Opus** — reserve for chunks with real design risk: a novel mechanic touching multiple systems at once (M1, R1, R2, R3, R4, R5's design phase), or untangling a gnarly bug (like this session's stat-realism investigation, which took real iterative reasoning). Costs more per token, but a chunk like that done wrong in Sonnet often costs MORE overall once you count the rework.

4. **Tier your test-verification effort by risk, don't run the full twice-suite for everything:**
   - Engine/stats-affecting chunks (M1, M2, R1-R5): keep the full "run the suite twice" discipline — these can silently corrupt stats the way the box_score.py rushing bug did this session.
   - Pure UI/template chunks (M3, M4, M5, M6, R8): one test run + one live-browser check via the preview tools is enough. Don't burn tokens re-running an 8-minute full suite twice for a template change that can't touch game state.

5. **Bundle small chunks into an already-warm session.** Once a session has HANDOFF.md/ROADMAP.md loaded, the dev server running, and context established, a second small chunk in the same session is cheaper than a second fresh session's startup cost. M5+M6 and R6+R7 are natural pairs.

6. **Don't re-run the stat-realism scratch-audit scripts from this session.** `tests/test_stat_realism.py` is now a permanent, checked-in regression gate — trust it. Only reach for a fresh one-off audit script if you're investigating a genuinely NEW reported anomaly, the way this session's work started.

7. **Point new sessions at real source, don't make them re-derive it.** The Figma export is already extracted to `docs/figma-export/` in the repo — a fresh session should read the specific `.tsx` file for its page, not re-request the zip or guess at layout from screenshots.

If a session doing M1 starts wanting to build return yardage too, that's the moment to stop and open a fresh R2 session instead, not push through in the same one.

9. **Use `/loop` or extended autonomous work only for chunks that are already well-scoped** (i.e., anything in the tables above). Open-ended "keep improving things" autonomous sessions are the most expensive mode there is, because most of the token spend goes to self-directed exploration rather than building.
