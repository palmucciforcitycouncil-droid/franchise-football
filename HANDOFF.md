## Architecture (decided this session, not inherited)

**One Python process. No REST API, no separate frontend.** FastAPI serves server-rendered Jinja2 templates directly. This was a deliberate reversal of what earlier GDD drafts specified (a FastAPI JSON API consumed by a separately-built JS frontend) — the repo's own history (two abandoned React/Vite rebuilds under the now-archived `_legacy/app/ui/figma*`, and a multi-day "revert to golden" cycle on an unmerged dashboard branch) was the deciding evidence that the API+frontend split was pure coordination overhead for a single-player local game. See GDD v4.1's Version History entry for the full reasoning.

- **Web/HTML:** FastAPI + Jinja2 (`app/templates/`). No htmx yet — current pages use plain HTML forms. Dark/blue/gold theme per GDD §10.2.
- **Player data:** SQLModel + SQLite (`app/models/player.py`, `app/core/db.py`), backed by the real roster import.
- **Season/schedule state:** plain dataclasses (`app/services/season_state.py`) persisted as JSON (`app/services/save_service.py`, `data/saves/current_season.json`, gitignored) — not in the SQL DB. This is intentional; season state is simple enough that JSON save/export (GDD §8) is a better fit than a DB table.
- **`_legacy/`** holds the old, pre-this-session `app/` and `tests/` trees, archived not deleted — an earlier audit found 3+ competing, half-broken simulation implementations in there. **Its trade engine and draft logic were checked as of 2026-09-07 and are NOT salvageable as code** -- `_legacy/app/services/trade_engine.py`, `draft_service.py`, `trade_value.py`, etc. all depend on the same abandoned September-2025-prototype schema as the DTO layer (integer `team_id`/`player_id`, plus a whole constellation of models that don't exist in the current codebase at all: `PlayerContract`, `TradeBlock`, `DraftPickInventory`, `cap_compliance`, `event_log_service`) -- building the real thing later means building Contracts/Cap first, then Trades/Draft on top, not porting this. It's also duplicated 2-3x across `_legacy/app/` and the abandoned `_legacy/app/ui/figma/dashboard-vite/` React rebuild, and at least one piece is provably broken, not just incompatible: `draft_service.py` imports a `DraftPick` symbol from `app.models.draft` that file never actually defines (only `DraftPickInventory`) -- a real "looked done, never executed" case, confirming the original audit's finding first-hand. **What IS worth reusing when Trades/Draft eventually get built for real:** `trade_value.py`'s `PICK_CHART` (a Jimmy-Johnson-style draft pick trade value table by round/slot) and `_age_curve()` (a player-value age curve peaking at 26-29) are pure, schema-independent formulas with no dependency on the broken parts -- worth porting as reference values, not the surrounding code.

## Running it

```bash
cd /c/FranchiseFootballGame
python -m venv .venv                    # if .venv doesn't exist yet
./.venv/Scripts/python.exe -m pip install fastapi uvicorn jinja2 python-multipart python-dotenv sqlmodel pytest httpx
```

**If `data/franchise_football.db` doesn't exist yet** (fresh clone), the app will still start but most routes will crash — you need real player data first:
```bash
./.venv/Scripts/python.exe scripts/import_players.py
```

16. **Fixed a real cross-restart determinism bug** (`app/engine/rng.py`'s new `stable_seed()`) — found while surveying the September 2025 prototype (recommended next step #3) for salvageable pieces, specifically its `make_rng()` helper. `main.py`'s `/simulate` route, `season_state.py`'s `simulate_current_week`, and `main.py`'s season-game view all derived their RNG seed with Python's builtin `hash((league_seed, home_abbr, away_abbr, ...))` -- and Python randomizes string hashing per-process by default (on since 3.3, no `PYTHONHASHSEED` pinned anywhere in this project), so the exact same matchup produced a *different* seed, and therefore a different simulated result, every time the server restarted. Verified empirically: `hash((2025, "KC", "BUF", "demo_game"))` gave three different values across three separate `python -c` invocations. This silently contradicted the app's own displayed claim ("deterministic: replaying these two teams with this seed always produces this result") and the GDD §1.3 determinism policy -- not a new bug introduced this session, this pattern (and an honest comment flagging it as a future `make_rng()` TODO) predates this session's other work. `schedule.py`'s one remaining `hash((seed, attempt))` call was checked and left alone -- both operands are plain ints, and Python's int hashing is *not* randomized, confirmed empirically the same way. New `stable_seed(*parts)` uses BLAKE2b instead of `hash()`. 3 new tests in `tests/test_rng.py`, including one that actually spawns fresh subprocesses to prove the fix (a same-process test can't catch hash randomization, since a process's hash seed is fixed for its own lifetime). Verified live end-to-end: simulated KC @ BUF, killed the server, started a fresh process, re-simulated the identical matchup -- same `game_seed` (2159590338) and same score (Buffalo 48) both times, which was NOT true before this fix.

18. **Real Penalty System** (`app/engine/drive_sim.py`'s `PenaltyOutcome` section, `tuning.py`'s new `penalty` params) — replaces the old flat-rate "Holding, offense: 5 yards" / "Defensive penalty: 5 yards" 50/50 coin flip with 5 real types, real attribution, and real accept/decline, per GDD §6.9 (a deliberate subset, not the full catalog -- see the Known Gaps entry). **Pre-snap** (rolled before play type is even decided, always enforced -- there's no completed play yet to compare against): False Start and Delay of Game (offense, attributed to a random OL starter / the QB), Offside (defense, a random DL starter). **In-play** (rolled after the play's real result is known, restricted to `raw_pos` staying under 100 -- touchdowns, turnovers, and safeties are scoped out entirely, since real accept/decline gets genuinely complicated there, e.g. a defense can decline a holding call to let an interception return stand): Offensive Holding on run plays only, with real accept/decline logic split into a pure, independently-tested `_holding_would_be_accepted(distance, real_yards)` -- the defense (the beneficiary) only accepts if enforcing the 10-yard penalty leaves the offense worse off than the real play already did, so a run stuffed for a bigger loss than the penalty correctly gets declined; and Defensive Pass Interference on incomplete passes only, attributed to the *real* covering defender from that specific attempt (`_resolve_pass` now also returns `defender_name`, threaded through from `choose_pass_target`'s result) rather than a random guess, always "accepted" (a spot foul + automatic first down is essentially always better than an incomplete pass, so no comparison needed). No `Team_Discipline_Modifier`/`Coach_Modifier`: neither a `discipline` player attribute nor a Coach entity exists in the real data, so attribution picks from the relevant personnel group rather than being rating-weighted -- same category of gap as `player_ai.py`'s documented composite-attribute mappings. 3 new tests, including a pure unit test of the accept/decline math and a statistical test proving DPI is attributed to a real secondary player, not a placeholder. One pre-existing test's assumption ("a penalty should replay the same down") had to be corrected -- a penalty with an automatic first down (DPI) genuinely should reset to 1st down, unlike the old system where every penalty just replayed the same down. Verified live: simulated several games, saw all 5 types fire with real player names (Joe Thuney, Von Miller, Xavien Howard, etc.); re-measured full-season scoring (272 games) at 48.4 combined -- barely moved from the pre-penalty-system 50.0 baseline -- with 7.9 penalties/game (plausible for a 5-type subset vs. real NFL's ~12-13 across a dozen-plus types); no server errors.
   - **Extended to 7 types, same session:** added Illegal Formation (offense, pre-snap, same treatment as False Start) and Roughing the Passer (defense, in-play, rolled only on sacks, 15 yards + automatic first down). Roughing is attributed to the real blitzer when the play was a blitz call (`DefensiveCall.blitz.blitzer`), or a random defensive lineman otherwise -- real football logic (a blitzer arriving a beat late is who's most likely drawing the flag), not a random guess across the whole defense. 1 new test verifying blitzer attribution. 19. **Score Fidelity System** (`app/engine/power_rating.py`, `app/engine/score_fidelity.py`, GDD §6.2 + §7.2) — the full spec, built after Brian revisited the earlier deferral decision. This engine derives outcomes bottom-up from real player attributes, the *opposite* of the GDD's assumed top-down "EP target -> abstracted per-drive TD/FG/Punt/TO table" architecture -- rather than replace the player-level engine (which would undo items 6-9, 17-18), EP anchoring is layered on as a small, bounded per-game multiplier. **Built faithfully:** Team Power Rating (Elo, §7.2 -- baseline 1500, K=20, HFA=55, MOV-dampened, zero-sum, persisted per team in the season save as `TeamRecord.power_rating`, exposed in the UI as "Power Ranking" on the Season and Dashboard standings tables); pre-game win probability + parity/upset model (§6.2.1-6.2.2, extreme records only adjusted after Week 10); EP anchoring as a per-game `MatchupContext.ep_multiplier` (favored team boosted, underdog penalized, proportional to win probability, plus a small home-scoring edge and a per-game noise draw), read by `_resolve_pass`/`_resolve_run` to nudge completion odds and yardage -- computed from the *same seeded RNG* the game itself uses, so season replays with the same `LEAGUE_SEED` stay fully deterministic; weekly feedback loop closing on season/rolling PPG error (§6.2.4's strictest, most measurable target) with a clamped delta, GDD-specified EMA damping (α=0.35), and a persisted telemetry log (`Season.sfs.telemetry`) showing the multiplier's correction week over week. **Deliberate scope cuts, documented in `score_fidelity.py`'s module docstring:** no true per-quarter EP/Dirichlet tracking (the engine has no quarter/clock model, just a two-minute-drill proxy -- approximated with one per-game noise draw instead of four per-quarter draws); `pace_factor`/`strength_factor` omitted from the EP formula (already modeled directly elsewhere -- including them again would double-count); no Red Zone Module or endgame PAT-decision logic (need real RZ-trip/2-point telemetry this engine doesn't track); weekly feedback only closes the PPG loop, not the GDD's GSM/PN/QBM/MIX multipliers (that pseudocode references undefined symbols with no formulas given -- only the PPG piece was concrete enough to implement faithfully rather than guess at); no formal tolerance-enforcement harness (verified empirically instead, like the original hand-tuned calibration pass); `regress_to_mean()` (§7.2's season-rollover regression) has no call site since this project only ever models one season at a time -- wire it in once multi-season progression exists. 15 new tests across `test_power_rating.py`, `test_score_fidelity.py`, and two new integration tests in `test_season.py`. ## Working patterns this session established (worth keeping)

- **Verify by running, not just reading.** Nearly every real bug found this session (tuning-parameter mismatches, distance-to-go not increasing on a loss, an outcome field silently overwritten, the inter-conference rotation formula breaking for odd season numbers) was caught by actually executing code and checking output, not by code review. Several were in code that "looked correct."
- **Test files exist for exactly this reason** — `tests/test_drive_sim.py`, `tests/test_player_ai.py`, `tests/test_season.py`, `tests/test_player_model.py` all check real invariants (not just "does it run"), several written *because* a manual check caught a bug that a shallower test wouldn't have.
- **Document simplifications where you make them**, in the code, not just in chat — every module above has a docstring explaining what it deliberately doesn't do yet and why. Keep that up.
- **Update the GDD when the implementation reveals the spec needs to change**, don't let them drift apart silently (this happened with §3.1 already, once).
