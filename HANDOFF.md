**When Brian returned, he pushed back on the UI focus** ("I tend to drift toward UI... we need to make sure there are no serious stat outliers") after spotting two DPOY leaders with 30+ sacks by week 9 on the live Stats page (no real player has ever recorded more than 22.5 in a season) and asked for a broad statistical-realism audit against real NFL benchmarks, floating Poisson-distribution validation as an idea. **This became item 36, the most significant engine bug found this session.** A full simulated 18-week season showed the sack leader had 65 sacks, but also passing (7410 yds/76 TD vs real records 5477/55), rushing (3093 yds vs record 2105), receiving (4864 yds/52 TD vs records 1964/23), and solo tackles (430 vs a ~190 realistic ceiling) were ALL inflated 1.5-3x real records -- and always concentrated on ONE player per team (a WR catching 62% of his team's targets). Root cause: THREE separate "who's involved in this play" pickers used pure or barely-tempered deterministic argmax over STATIC per-game ratings -- `decide_blitz`'s blitzer pick and `choose_run_point_of_attack`'s run-zone pick had zero randomization at all, and `choose_pass_target`'s existing softmax (fixed for this exact bug class in an earlier session) was tempered far too low (4.0-7.0) for how wide this engine's ~0-99 Madden-attribute-based mismatch scores actually run -- so the single best-rated player/zone won on every relevant play of a game, and usually of a whole season. Fixed by converting all three to real weighted-random (softmax) selection, empirically retuning temperatures against full-season simulation output rather than guessing (final: `TARGET_TEMPERATURE_NORMAL/CLUTCH` 120/70, `ZONE_TEMPERATURE` 200, `BLITZER_TEMPERATURE` 45, all in player_ai.py/defensive_ai.py), plus two secondary rate fixes measured the same way: `SACK_CONVERSION_RATE` (drive_sim.py) scaled down since per-dropback sack probability was running ~2x real, and `pace_drives()` (rating.py) rescaled since average total plays/game were running ~18% over real NFL rates. On Brian's Poisson question: agreed it's the right tool for VALIDATING the sacks-per-game distribution (a new test checks mean-in-range AND variance-approx-mean, Poisson's defining property) but not for GENERATING sacks, since this engine simulates real individual attributed plays -- a correctly-calibrated sum of many independent low-probability per-play Bernoulli trials is a Poisson process by construction, so fixing the per-play math was the right layer. Final verified state (full 18-week sim): 2.2-2.6 team sacks/game (real ~2.4-2.6), sack leader 15-21 (real record 22.5), INT leader 7-11 (real record 14), 64-65 total plays/team/game (real ~63-65), solo tackle leader 150-190 (real ceiling ~190-200), target share down from 62% to ~33-38% (real ceiling ~28-30%, still a bit high, disclosed). **One real, disclosed residual gap: TFL still runs ~40-44 vs a realistic ~30-35 ceiling** -- further temperature/rate tuning had diminishing, noisy returns on this specific category; a new `tests/test_stat_realism.py` (two tests: full-season leader/rate bounds against real records with generous headroom, and the Poisson mean/dispersion check) permanently guards against regression and gives the TFL gap extra disclosed headroom (1.5x vs 1.35x everywhere else) rather than hiding it. One existing test (`test_run_point_of_attack_matches_best_blocking_zone_most_of_the_time`) needed its threshold and docstring updated to reflect the new intentionally-near-uniform zone selection. **Brian then asked a sharper follow-up question that became item 37, the single biggest build of this session:** does the whole stat distribution -- not just leaders, but average and below-average players too -- match real NFL variance? It didn't, and this project's own imported real NFL data (`data/saves/history.json`, `scripts/import_nfl_history.py`) made that measurable directly rather than relying on memorized benchmarks: a full simulated season vs. the real 2025 NFL season (same qualification thresholds) showed real NFL credits solo tackles to 1384 distinct defenders/season (median 7) against this engine's 352 (median 67, a real 9.6x gap at the median) -- because literally every offensive/defensive snap of an entire season went through the same fixed 11 starters per team, zero substitution, zero committee backfield, zero WR depth beyond 4 pass-catchers, zero defensive rotation. Real NFL has ~250 qualified receivers (20+ targets); this engine had 128. Root cause was structural, not a probability bug like item 36 -- there was no roster-depth modeling of any kind.

Built new `app/engine/rotation.py`: real snap/touch-share modeling from (1) depth-chart rank, position-specific geometric decay hand-calibrated to real usage patterns (a workhorse RB's ~60% carry share vs. heavy DL rotation vs. minimal safety rotation), and (2) each player's own `durability` (Madden's Injury rating) + `stamina` -- Brian's explicit request ("tied into individual players attributes, like injury and any stat we have for stamina... consider what else plays a role"). Age and overall_rating were considered and deliberately left out: age's real effect is already substantially reflected in durability for an older player in this Madden-derived data, and overall_rating already determines starter/backup ORDER itself, so folding either in again would double-count a signal rather than add one. This is a season-long workload-distribution proxy, not a live in-game injury system (none exists -- Post-MVP).

Wired in everywhere a fixed single player used to be assumed:

## Architecture (decided this session, not inherited)

**One Python process. No REST API, no separate frontend.** FastAPI serves server-rendered Jinja2 templates directly. This was a deliberate reversal of what earlier GDD drafts specified (a FastAPI JSON API consumed by a separately-built JS frontend) — the repo's own history (two abandoned React/Vite rebuilds under the now-archived `_legacy/app/ui/figma*`, and a multi-day "revert to golden" cycle on an unmerged dashboard branch) was the deciding evidence that the API+frontend split was pure coordination overhead for a single-player local game. See GDD v4.1's Version History entry for the full reasoning.

- **Web/HTML:** FastAPI + Jinja2 (`app/templates/`). No htmx yet — current pages use plain HTML forms. Dark/blue/gold theme per GDD §10.2.
- **Player data:** SQLModel + SQLite (`app/models/player.py`, `app/core/db.py`), backed by the real roster import.
- **Season/schedule state:** plain dataclasses (`app/services/season_state.py`) persisted as JSON (`app/services/save_service.py`, `data/saves/current_season.json`, gitignored) — not in the SQL DB. This is intentional; season state is simple enough that JSON save/export (GDD §8) is a better fit than a DB table.
- **`_legacy/`** holds the old, pre-this-session `app/` and `tests/` trees, archived not deleted — an earlier audit found 3+ competing, half-broken simulation implementations in there. **Its trade engine and draft logic were checked as of 2026-09-07 and are NOT salvageable as code** -- `_legacy/app/services/trade_engine.py`, `draft_service.py`, `trade_value.py`, etc. all depend on the same abandoned September-2025-prototype schema as the DTO layer (integer `team_id`/`player_id`, plus a whole constellation of models that don't exist in the current codebase at all: `PlayerContract`, `TradeBlock`, `DraftPickInventory`, `cap_compliance`, `event_log_service`) -- building the real thing later means building Contracts/Cap first, then Trades/Draft on top, not porting this. It's also duplicated 2-3x across `_legacy/app/` and the abandoned `_legacy/app/ui/figma/dashboard-vite/` React rebuild, and at least one piece is provably broken, not just incompatible: `draft_service.py` imports a `DraftPick` symbol from `app.models.draft` that file never actually defines (only `DraftPickInventory`) -- a real "looked done, never executed" case, confirming the original audit's finding first-hand. **What IS worth reusing when Trades/Draft eventually get built for real:** `trade_value.py`'s `PICK_CHART` (a Jimmy-Johnson-style draft pick trade value table by round/slot) and `_age_curve()` (a player-value age curve peaking at 26-29) are pure, schema-independent formulas with no dependency on the broken parts -- worth porting as reference values, not the surrounding code.

## What's actually built and verified (not just claimed)

Every item below was tested (pytest) *and* verified live in a browser render, per this session's working pattern — the whole reason that pattern exists is that a prior audit found a lot of "looks done" code in `_legacy/` that had never actually been run.

1. **Single-game simulator** (`GET /`, `POST /simulate`) — pick two teams, simulate one game.
2. **Full season** (`GET /season`, `POST /season/simulate-week`, `POST /season/reset`) — real GDD schedule formula (§5.1): 6 divisional + 4 intra-conference rotation (3-yr cycle) + 4 inter-conference rotation (4-yr cycle) + 2 standings-based + 1 "17th game." 17 games/team, 18 weeks, verified against the exact 6/4/4/2/1 breakdown. **Known simplification:** bye weeks aren't confined to the GDD's "weeks 5-14 except 6" window — see `app/engine/schedule.py`'s docstring for why (forcing that window turns week-placement into a much harder problem; bye *timing* doesn't affect any gameplay logic, so this was a deliberate, documented scope cut, not an oversight).

4. **Down-by-down Drive Engine** (`app/engine/drive_sim.py`) — real down/distance/field-position sequence, not one dice roll per drive. Includes safety detection, a real (partial-catalog) Penalty System (item 18 below), a simplified 4th-down go/kick/punt heuristic.

GDD §3.1 documents the schema and two deliberate naming decisions (`durability` keeps Madden's own polarity rather than being inverted to match the Post-MVP `injury_proneness` framing; `salary`/`signing_bonus` are stored now even though Contracts is Post-MVP).

## Working patterns this session established (worth keeping)

- **Verify by running, not just reading.** Nearly every real bug found this session (tuning-parameter mismatches, distance-to-go not increasing on a loss, an outcome field silently overwritten, the inter-conference rotation formula breaking for odd season numbers) was caught by actually executing code and checking output, not by code review. Several were in code that "looked correct."
- **Test files exist for exactly this reason** — `tests/test_drive_sim.py`, `tests/test_player_ai.py`, `tests/test_season.py`, `tests/test_player_model.py` all check real invariants (not just "does it run"), several written *because* a manual check caught a bug that a shallower test wouldn't have.
- **Document simplifications where you make them**, in the code, not just in chat — every module above has a docstring explaining what it deliberately doesn't do yet and why. Keep that up.
- **Update the GDD when the implementation reveals the spec needs to change**, don't let them drift apart silently (this happened with §3.1 already, once).
