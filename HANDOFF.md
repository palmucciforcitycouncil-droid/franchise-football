## Architecture (decided this session, not inherited)

**One Python process. No REST API, no separate frontend.** FastAPI serves server-rendered Jinja2 templates directly. This was a deliberate reversal of what earlier GDD drafts specified (a FastAPI JSON API consumed by a separately-built JS frontend) — the repo's own history (two abandoned React/Vite rebuilds under the now-archived `_legacy/app/ui/figma*`, and a multi-day "revert to golden" cycle on an unmerged dashboard branch) was the deciding evidence that the API+frontend split was pure coordination overhead for a single-player local game. See GDD v4.1's Version History entry for the full reasoning.

- **Web/HTML:** FastAPI + Jinja2 (`app/templates/`). No htmx yet — current pages use plain HTML forms. Dark/blue/gold theme per GDD §10.2.
- **Player data:** SQLModel + SQLite (`app/models/player.py`, `app/core/db.py`), backed by the real roster import.
- **Season/schedule state:** plain dataclasses (`app/services/season_state.py`) persisted as JSON (`app/services/save_service.py`, `data/saves/current_season.json`, gitignored) — not in the SQL DB. This is intentional; season state is simple enough that JSON save/export (GDD §8) is a better fit than a DB table.
- **`_legacy/`** holds the old, pre-this-session `app/` and `tests/` trees, archived not deleted — an earlier audit found 3+ competing, half-broken simulation implementations in there. **Its trade engine and draft logic were checked as of 2026-09-07 and are NOT salvageable as code** -- `_legacy/app/services/trade_engine.py`, `draft_service.py`, `trade_value.py`, etc. all depend on the same abandoned September-2025-prototype schema as the DTO layer (integer `team_id`/`player_id`, plus a whole constellation of models that don't exist in the current codebase at all: `PlayerContract`, `TradeBlock`, `DraftPickInventory`, `cap_compliance`, `event_log_service`) -- building the real thing later means building Contracts/Cap first, then Trades/Draft on top, not porting this. It's also duplicated 2-3x across `_legacy/app/` and the abandoned `_legacy/app/ui/figma/dashboard-vite/` React rebuild, and at least one piece is provably broken, not just incompatible: `draft_service.py` imports a `DraftPick` symbol from `app.models.draft` that file never actually defines (only `DraftPickInventory`) -- a real "looked done, never executed" case, confirming the original audit's finding first-hand. **What IS worth reusing when Trades/Draft eventually get built for real:** `trade_value.py`'s `PICK_CHART` (a Jimmy-Johnson-style draft pick trade value table by round/slot) and `_age_curve()` (a player-value age curve peaking at 26-29) are pure, schema-independent formulas with no dependency on the broken parts -- worth porting as reference values, not the surrounding code.

20. **Fixed a real concurrency bug Brian found by actually using the app** (`app/services/season_state.py`'s `_STATE_LOCK`) — he reported a team sitting at 20-0 with `current_week` at 21 in an 18-week season. Root cause: `/season/simulate-week` and `/season/reset` (`app/main.py`) are plain `def` routes, which FastAPI runs in a thread pool -- so two requests (a double-click, a slow request retried, a page reload resubmitting the form) can genuinely execute concurrently on different threads. `simulate_current_week()`'s read-`current_week` / simulate / increment / save sequence was not atomic: two overlapping calls could both read the same `current_week` before either incremented it, both simulate the same week (inflating that week's teams' win/loss counts), and `current_week` could end up past `N_WEEKS` entirely with no bound. Underlying per-play formulas in `tuning.py`/`drive_sim.py` are still hand-tuned constants -- the SFS layers a self-correcting multiplier on top of them rather than replacing them, so don't hand-tune those constants further without a reason; the weekly feedback loop is now what's supposed to absorb drift, not manual retuning.

- **Playoffs has two disclosed simplifications, not GDD-literal** (item 24 above) — no real neutral-site Super Bowl model (the better seed is just designated "home" for engine bookkeeping) and no simulated overtime (a tied score goes to the home team, same as the regular season already does, instead of the GDD's specified 15-minute-period model, since there's no clock/quarter model to run one). Both are documented in `app/engine/playoffs.py`'s own module docstring.
- **DPOY and Progression's F_use are now real multi-stat, not interception-only (item 30)** — a real defensive box score system (`app/engine/defensive_box_score.py`) now attributes solo tackles, sacks, TFL, INT, PD, FF/FR, and Defensive TD (item 38, ROADMAP.md M1) to real named defenders, built on disclosed heuristics in `drive_sim.py` (`_sack_defender`, `_run_tackler`, `_defensive_td_probability`). DPOY is a real weighted composite across all of those; Progression's F_use is real for DL/LB/DB. OL/K/P still get Progression's neutral 1.0 usage default (no real per-play usage stat exists for them either). Also disclosed: crediting the SAME covering defender with every completed reception's tackle (no second, pursuing-defender model for YAC tackles) means a heavily-targeted CB's tackle total can run higher than real NFL tackle leaderboards (usually LBs/safeties) — see `defensive_box_score.py`'s own docstring for the full detail.
- **Real NFL data seeding is now built (item 31)** — `scripts/import_nfl_history.py` seeds real 2002-2025 NFL standings/champions/season stats via nflverse (`nflreadpy`, CC-BY 4.0), real seasons prepended before simulated ones on one continuous timeline. **Real, disclosed scope limits, not oversights**: no real playoff seeds/bracket imported (the GDD's full tie-breaker chain applied to real historical standings is a substantial separate undertaking); real awards are computed by this engine's own formula against real stats, not looked up as the actual real-world AP winners; no real historical Power Rating exists to import (every imported season gets the same 1500.0 baseline); HOF induction for real players is NOT separately seeded from a real inductee list -- it happens automatically through the existing `hall_of_fame()` formula once real stats are archived, so it only reaches players whose careers fall substantially within 2002-2025. **Coaches and O-line still have no real stat-based formula this engine could evaluate them by**, even with real data available -- no individual OL stat exists in this engine at all, and no Coach entity exists yet (Post-MVP) -- a real, disclosed limit on how complete real-NFL seeding can ever be without further engine work. Wikipedia's real HOF inductee list was researched as a viable low-risk source (bare facts, not copyrightable expression) but deliberately not used -- see item 31's own note for why the season-stats approach alone was judged sufficient for this pass.
- **Career-cumulative stats and real HOF induction now exist (item 29)** — `history_store.py`'s `career_stats()`/`hall_of_fame()` sum a player's full stat line across every archived season and induct by a disclosed composite-score threshold. Career identity is `(team_abbr, name)`, not `Player.player_id` -- deliberately disclosed as safe only because no trade/free-agency/roster-movement system exists yet (a player's team never changes across their career in this engine); revisit once trades exist. No "Career" stats TAB/page exists yet -- `career_stats()` is a real, tested function with no UI consumer besides `hall_of_fame()` itself; a dedicated Career view (e.g. from a player's Roster row) is still a real gap if that's ever wanted.
- **Scouting report has three real data gaps, not laziness** (item 23 above) — no pass-depth (quick/standard/deep) mix, no target-distribution breakdown, and no return-game averages, because `PlayEvent` and the special-teams engine don't track the underlying data at all (not "don't track it well," don't track it). Adding those means extending `PlayEvent` (a depth-of-target field, a receiver-rank field) and building real return-yardage simulation in `drive_sim.py`'s punt/kickoff handling first -- this isn't a scouting.py fix, it's upstream engine work.
- **The three open design questions the v4.4 GDD rewrite surfaced are resolved (v4.5, 2026-09-07)** — Awards Race/Players of the Week (Stats) and League Record Book/Super Bowl History (HOF) are kept in MVP scope, spec'd fresh; Calendar is confirmed cut from Part 1 nav; the team-selection screen has a minimal spec, **now built** (item 21 above). The Awards Race and HOF-history additions themselves are still design-scope resolution only, not built yet.
- **Individual stat realism was audited against real NFL benchmarks and mostly fixed (items 36-37)** — see items 36-37's own entries above for the full bug/fix detail (three deterministic "who's involved" pickers, an inflated sack rate, inflated drive pace, and then a much bigger structural gap: no roster-depth/rotation modeling at all, fixed by `app/engine/rotation.py`). **What's still disclosed as not fully resolved**: DEF solo tackles remains the least-closed category (~2-3x real at the mean/median even after rotation.py, vs ~9.6x before -- see item 37); TFL still runs ~40-44 in a simulated season vs a realistic ~30-35 ceiling (`tests/test_stat_realism.py` tracks both with deliberately extra headroom, not a claim they're fixed); top-end WR target share (~33-38%) is closer to real (~28-30% ceiling) but not fully there; passing/rushing/receiving league leaders now land close to real all-time records rather than 1.5-3x over them, but "close to the record" for a simulated league's best-of-32 season is itself worth another look if it recurs often across many seeds, not just the one seed each pass validated against. QB pass-yardage distribution runs structurally high (mean/median ~1.4x real) because this engine has no backup-QB/in-season-injury system at all -- one QB starts literally every game, unlike real NFL's real distribution across more passers -- a genuinely different, disclosed gap (Post-MVP) from the rotation.py fixes, not something rotation.py could address on the offensive skill-position side.

## Working patterns this session established (worth keeping)

- **Verify by running, not just reading.** Nearly every real bug found this session (tuning-parameter mismatches, distance-to-go not increasing on a loss, an outcome field silently overwritten, the inter-conference rotation formula breaking for odd season numbers) was caught by actually executing code and checking output, not by code review. Several were in code that "looked correct."
- **Test files exist for exactly this reason** — `tests/test_drive_sim.py`, `tests/test_player_ai.py`, `tests/test_season.py`, `tests/test_player_model.py` all check real invariants (not just "does it run"), several written *because* a manual check caught a bug that a shallower test wouldn't have.
- **Document simplifications where you make them**, in the code, not just in chat — every module above has a docstring explaining what it deliberately doesn't do yet and why. Keep that up.
- **Update the GDD when the implementation reveals the spec needs to change**, don't let them drift apart silently (this happened with §3.1 already, once).
